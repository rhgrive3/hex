# hex — アプリの中身を、日本語で読むツール

iPhone / iPad / Mac アプリの実行ファイル（Mach-O）や生のバイナリを開いて、
**「調べたいこと」から、担当している関数・命令・アドレスまで案内する**ためのツールです。

大量の解析結果を並べるビューアではありません。やっているのはこの 5 つです。

```
バイナリから事実を取り出す（参照関係・制御フロー・データフロー）
  → 関係を解析する（誰が誰を呼び、誰が何を見ているか）
    → 根拠を示して意味を推定する（掛け算の内訳まで開示する）
      → 仮説を逆アセンブルして裏を取り、1 個に決める（決まらなければそう言う）
        → 目的の値・処理・命令・バイトまで案内する
```

**目的を選ぶだけで、その値が 1 個に決まります。**
「HP らしき候補が 40 個」ではなく「`BattleManager.hp`（+0x20）です。
`-[BattleManager hp]` を逆アセンブルして確かめました」まで出します。

アセンブリを触ったことがない人が、ゼロから読めるようになることを目標にしています。
iPad（iPad mini 6 の縦・横で調整）の Safari で快適に動くように作ってあります。

**閲覧専用です。** 開いたファイルは書き換えられず、どこにも送信されません。
Mach-O の解析も、逆アセンブルも、検索も、すべて端末の中の Web Worker で動きます。

```
アドレス      命令                        意味
1000003D4    stp   x29, x30, [sp, #-0x10]!
  ▼ _greet   戻り先アドレス (x30) と、呼び出し元のフレーム位置 (x29) をスタックに保存する。
             関数の始まりの合図です。
1000003DC    adrp  x0, #0x100000000
             x0 に 0x100000000 を入れる。これは 4096 バイト単位に切り下げた「おおまかな住所」です。
1000003E0    add   x0, x0, #0x43c
             x0 に 0x43C（10進で 1084）を足して x0 に入れる。 → 0x10000043C
1000003E4    bl    #0x100000430
             _puts を呼び出す。終わったらこの次の行に戻ってきます。
```

## 開いた瞬間に、勝手に解析が終わっている

ファイルを開くと、**何も押さなくても** 次のことを全部やります（`js/auto.js`）。

```
1. クラスと、その中の値の名前を読む   Objective-C のクラス表（← いちばん効く）
2. セクションを 1 周して索引を作る    呼び出しの辺・データ参照・語ごとの命令分類
3. 文字列を集めて機能ごとに分ける      ログイン / 課金 / バトル / 通信 …
4. アプリを部品に畳む                 数万の関数 → 十数個の「部品」
5. 16 個の目的すべてを総当たりで採点   HP・攻撃力・ダメージ・コイン・ガチャ・通信 …
6. 目的ごとに値を 1 個まで絞り、命令で裏を取る  ← ここで「候補」が「答え」になる
7. 気づいたことを拾う                  通信先 / 改造検知 / 暗号 / 広告 / 課金
8. 上位の関数だけ、命令まで踏み込む     値を書き換えている場所を自動で見つける
9. その関数に、アプリの言葉で名前を付ける  sub_1001A74E4 →「アイテムを 1 増やす処理」
```

## 候補を並べるのをやめた。1 個に決めて、命令で裏を取る

このツールがいちばん変えたのはここです。

これまでは「HP を選ぶ → 候補が 40 個出る → 上から順に自分で確かめる」でした。
これでは**もともと解析できる人しか使えません**。40 個から選べる人は、
そもそもこのツールを必要としていない。だから流れをひっくり返しました。

```
❤️ HP・体力 を選ぶ
   ↓
確定
逆アセンブルまで降りて確かめました。これで間違いありません。

BattleManager.hp
4 バイトの整数  ·  先頭から 0x20  ·  4 バイト

  確からしさ            99.9% 以上
  調べた値の数          18,420 個の中から
  2 番目の候補との差    93,000 倍
  実際に読んだ処理      6 個
```

決め手は「クラス表にそう書いてあるから」ではありません。
**そう書いてあることを、命令で確かめたから**です。

```
なぜ、これだと言えるのか

 -[BattleManager hp] を実際に逆アセンブルしたところ、
   本当にこの位置（+0x20）を読んで返していた（ほかの位置は触っていない） 〔検証済〕 ×40
 -[BattleManager setHp:] を逆アセンブルしたところ、
   本当にこの位置へ引数の値を書き込んでいた                              〔検証済〕 ×40
 クラス表に書かれている名前が「_hp」そのものである                        〔事実〕  ×55
 この値を読んで、計算して、同じ場所へ書き戻している命令が実在する
   （0x10000040C）                                                       〔検証済〕 ×2.5
 持ち主の BattleManager が、バトルを担当する部品に分類されている          〔推測〕  ×3
 型が数値（4 バイトの整数）で、探しているものと合う                       〔事実〕  ×2.2
 同じ BattleManager の中に、関係する値が 3 個そろっている                 〔推測〕  ×1.6
```

右の数字は点数ではなく **倍率** です。「その根拠があると、
確からしさが何倍になるか」をそのまま出しています。
18,420 個の値がある中の 1 個なので、出発点は 0.005%。
そこにこの倍率を掛けていって 99.9% を超えます（`js/evidence.js`）。

### 「確定」を名乗る条件は厳しくしてあります

確定できないものを確定と言うのは、何も言わないより悪いためです。
次の 4 つが**すべて**そろったときだけ「確定」と表示します。

| 条件 | なぜ |
| --- | --- |
| 逆アセンブルで確かめた根拠が 1 つ以上ある | 表に書いてあるだけでは、命令がそう動く証明にならない |
| 独立した種類の根拠が 3 つ以上ある | 名前の書き方が 3 通り当たっても、手がかりは 1 つでしかない |
| 確からしさが 99% 以上 | |
| 2 番目の候補より 20 倍以上あること | 1 位が 99% でも 2 位も 99% なら、決まっていない |

そろわなければ「**ほぼ確実**」「**絞りきれていません**」と正直に出して、
**何が足りないのか**まで書きます。

```
絞りきれていません
上位の候補が拮抗しているため、1 つに決めていません。
決めつけるより、両方を見てもらった方が確実です。

確定と言えない理由
 • 命令まで降りた裏取りがまだありません（アクセサが無いか、読めませんでした）
 • 2 番目の候補との差が小さく、どちらとも言えません
```

### 名前が読めないアプリでも、形から場所を出します

Swift だけで書かれたアプリや、名前を潰したアプリには Objective-C のクラス表がありません。
名前が 1 つも読めないので、上のやり方は使えません。

それでも **形** は読めます。ゲームの数値はどれも「読む → 計算する → 同じ場所へ書き戻す」
という形をしていて、しかも「ダメージ %d」のような文言を参照している関数の中にあります。
この 2 つが重なる場所はそう多くないので、そこまでは特定できます（`js/pinpoint.js`）。

```
ほぼ確実
オブジェクトの 0x30 にある値
4 バイト

 この場所を読んで、計算して、同じ場所へ書き戻している命令が実在する（0x100003008）
 目的に関係する文言を参照している処理の中にある
 3 個の処理が、同じこの場所を扱っている

確定と言えない理由
 • この値の名前がバイナリに残っていません。場所と形までは確かめられましたが、
   それが本当にこの目的の値かどうかは、名前からは裏付けられません
```

名前が付けられない以上、これを「確定」とは呼びません。
ただ「ここを書き換えれば変わります」と言うには十分な材料です。

## `sub_1001A74E4` に、アプリの言葉で名前を付ける

命令を 1 行ずつ説明できても、画面に `sub_1001A74E4` と出た瞬間に読む人は止まります。

> stp / ldr / add / str …は分かった。**で、これは何の処理なの？**

命令の説明は「どう動くか」には答えますが、「アプリの何の話か」には答えていません。
人が知りたいのは後者しかない。だから関数 1 つにつき 1 行の**名前**を作ります（`js/role.js`）。

```
🎒 アイテム・所持品を 1 増やす処理
```

作る名前は必ずこの形にそろえます。3 つに分けているのは、**証拠の出どころが違う**ためです。

| 要素 | 例 | 何から言えるか |
| --- | --- | --- |
| 動作（動詞） | 1 増やす / 10 減らす / 端末に保存する | **命令の形そのもの**。`ldr → add #1 → str` が実在すれば、推測ではなく事実 |
| 対象（目的語） | `ItemManager` の `itemCount` | クラス表があれば名前まで。無ければ「オブジェクトの +0x30」まで |
| 機能（話題） | 🎒 アイテム・所持品 | 参照している文言・メソッド名・クラス名・呼び出し元。**人が付けた名前にしか宿っていない** |

この分け方には実利があります。**動詞の証拠は、対象について何ひとつ言っていない**からです。
「+1 している」ことをどれだけ厳密に確かめても、それがアイテムなのかコインなのか
ログイン回数なのかは 1 ミリも決まりません。混ぜると
「+1 する処理はぜんぶアイテム獲得」という断定が出ます。だから証拠表（`js/evidence.js`）で
目的に結びつける印を付けてあるのは機能・対象の側だけで、`role-verb-*` には付けていません。

### 決まらなければ、名乗らない

本物のアプリの関数は、文言を何百本も参照します。そういう関数では「アイテム」と「スコア」の
両方に手がかりが立ち、どちらが勝つかは紙一重になります。勝った方だけを見出しに出すと、
**すぐ下の根拠と食い違った名前**が出ます（実際に出ました）。

そこで動作と機能は別々に決着させ、決まっていない方は名乗りません。

```
オブジェクトの +0x20 にある値を 1 増やす処理
絞りきれていません   確からしさ 2%

変えているのは オブジェクトの +0x20 にある値です。
アプリの機能は ⬆️ レベル・経験値 か 🎒 アイテム・所持品 のどちらかです。
手がかりが割れているので、1 つには決めていません。
```

動作（+1 している）は命令で確かめられているので言い切り、機能は言い切らない。
黙って消すのではなく、**何と何で迷っているのか**まで出します。

### なぜその名前なのかは、倍率で開示する

```
なぜ、この処理だと言えるのか

 この値を読んで、計算して、同じ場所へ書き戻している命令が実在する
   （0x1001A7760） — 加工しているのはここ                        〔検証済〕 ×8.8
 この関数が「drop_popup_chara_levelup1」という文言を実際に参照している 〔事実〕  ×6
 増減の量が命令に直接書かれている（1）ので、どれだけ変わるかまで読み取れる 〔検証済〕 ×3.8
 別の機能を指す手がかりも同じくらいあり、この機能だと言い切れない       〔推測〕  ÷2.9
 触っている値の名前がバイナリに残っていない（場所までは分かる）         〔推測〕  ÷2
```

下げる証拠も同じ場所に出します。上げる材料だけを並べるのは、点数の水増しと同じです。

### 一覧にも出る。ただし「たぶん」と書く

呼び出し元・呼び出し先・候補の一覧にも、この 1 行が付きます。
一覧の数十行を全部逆アセンブルするわけにはいかないので、そこは索引だけの**下見**です。

```
この関数を呼んでいる (2)
  sub_10031F850    たぶん 🎒 アイテム・所持品に関わる処理（判定）
```

下見には必ず「たぶん」を付けます。下見は値の書き換えまで見えていないので、
開いたときの結論と食い違うことがあり、**中身を読んでいない札の方が自信ありげに見える**のが
いちばん困るためです。言うことが無いときは、何も書きません
（どの関数にも当てはまる文を全行に並べても、手がかりは 1 つも増えません）。

## 数万の関数を、そのまま見せない

関数を 1 つずつ丁寧に説明できても、**数万個の中から目当ての 1 つを見つけるのは無理**です。
だから最初の画面は関数の一覧ではなく、**アプリの地図**にしてあります。

```
このアプリは、こういう部品でできています
  ⚔️ バトル・戦闘     12 クラス · 340 メソッド · 86 個の値   BattleManager, EnemyUnit …
  💳 課金・購入        4 クラス · 62 メソッド                ShopViewController, IAPManager …
  🌐 サーバー通信      8 クラス · 210 メソッド               APIClient, RequestBuilder …
  📱 画面・UI         96 クラス
  ❓ 分類できなかったもの  120 クラス
```

ここから下へ降りていきます。**1 画面に出るものは、常に十数個までです。**

```
部品（⚔️ バトル）
  → クラス（BattleManager）
    → そのクラスが持っている値（hp / attack / defense …）
      → その値を読み書きしている場所（書き込み 3 か所・読み出し 8 か所）
        → 処理 → 命令 → アドレス → バイト
```

部品分けの材料は 3 つとも独立しています。クラス名だけでは決めません。

| 材料 | 例 |
| --- | --- |
| クラス名 | `BattleManager` `ShopViewController` `APIClient` |
| そのクラスが実際に参照している文字列 | 「ダメージ %d」「購入を復元しています」 |
| そのクラスが実際に呼んでいる API の分類 | `NSURLSession` → 通信、`SecItemCopy` → 秘密情報 |

## `x0 + 0x20` を `self.hp` と読む

このツールでいちばん効く一手です。

配布用のアプリは自作の関数名が削られていますが、**Objective-C のクラスだけは
メンバ変数の名前・型・位置の表がバイナリに必ず残っています**。これを読むと、

```
ldr  w8, [x0, #0x20]        →   BattleManager の hp（4 バイトの整数）を読み込む
sub  w8, w8, w9             →   計算した値だけ減らす
str  w8, [x0, #0x20]        →   同じ hp へ書き戻す
```

まで戻せます。「x0 が指す場所の 0x20 バイト目」では何のことか分かりませんが、
「HP を減らしている」なら誰にでも分かります。

だから **「HP を探す」は、関数ではなく値（フィールド）から探せます**。

```
BattleManager.hp
  種類: 4 バイトの整数      位置: オブジェクトの先頭から 0x20

  3 か所で使われていました。うち書き込みは 2 か所です。
  このうち 1 か所は BattleManager 自身のメソッドの中なので、この値のことでほぼ間違いありません。

  -[BattleManager applyDamage:]   書き込み 2 か所 · 読み出し 1 か所   〔このクラス〕 ✎
```

同じ位置を触っている命令をすべて拾うので、**別のクラスの、たまたま同じ位置にある値**が
混ざることがあります。そこは「このクラス」「別のクラス」「クラス不明」の札で区別します。

## 説明は 3 段。既定はいちばん上だけ

具体的な説明は、具体的すぎると「で、何がしたい処理なの？」が消えます。
だから関数を開いて最初に見えるのは 1 行だけで、詳細は畳んであります。

```
-[BattleManager applyDamage:]        BattleManager のメソッド

  BattleManager の hp を計算した値だけ減らす処理です。      ← ひとこと（既定で見える）

  ・呼び出し元から 2 個の値を受け取ります。                  ← どういうこと（既定で見える）
  ・変えているのは BattleManager の hp（4 バイトの整数）です。
  ・計算した結果を、呼び出し元へ返します。
  ・この処理は 1 か所から呼ばれています。

  ▶ 詳しく見る（事実・推測・分からないこと）                ← 命令の話はこの下
```

そして最初の画面には、自動で見つけた「値を書き換えている場所」が並びます。

```
値を書き換えている場所（自動で見つけたもの）                        〔事実〕
  BattleManager の hp を計算した値だけ減らす
    -[BattleManager applyDamage:] · 0x10000040C
    「ダメージ計算」の候補として見つかりました

気づいたこと
  通信先（サーバーの住所）  https://api.example.com/v1/battle   3 か所から使われています
  解析・改造の検知らしきもの jailbreak detected                 1 か所から使われています

次にすること
  1. 値を書き換えている場所（0x10000040C）を開いて、何を増減させているか確かめる
  2. 「ダメージ計算」の最有力候補を開いて、根拠を確かめる
  3. 最後は実際に動かして、狙った値が変わるかどうかを確かめる

自動解析の範囲: クラス 812 個、その中の値 3,140 個、文字列 12,480 本、
呼び出しの辺 96,204 本、データ参照 41,880 件、関数 9,912 個。
このうち 12 個の関数は、実際に命令まで読んでいます。
```

**何をどれだけ見たかも隠しません。** 自動でやったからといって、
「全部見た」ふりはしません。深掘りしたのが 12 個なら 12 個と書きます。

コードが 24 MB を超えるファイルでは、自動走査を勝手に始めずに確認します
（待たされるのが分かっているのに黙って始めない、という考え方です）。

Objective-C のクラス表がないファイル（Swift だけ・C++・難読化済み）では、
文字列の分類から**粗い地図**を作り、画面にもそう書きます。

## そのうえで「何を調べたいですか？」から掘れる

自動解析の下には、いつでも目的から入り直せる入口があります。

```
何を調べたいですか？
  [❤️ HP・体力] [⚔️ 攻撃力] [🛡️ 防御力] [💥 ダメージ計算] [🪙 所持金・コイン]
  [🎰 ガチャ・抽選] [💳 購入・課金] [🔑 ログイン・認証] [📺 広告] [💾 セーブ・保存]
  [🌐 通信] [🏆 スコア] [⬆️ レベル・経験値] [⚡ スタミナ] [🎒 アイテム] [🚨 チート対策]
  または「敵にダメージを与える処理」のように、ふつうの言葉で入力
```

選ぶと、まず上に「**これです**」が出ます（前述の特定）。
その下に、関係のありそうな**処理**が根拠つきで並びます。
値が決まっていても、それを書き換えている処理は別に知りたいためです。

```
_apply_damage                              ★★★★☆  75%
  関数の名前「_apply_damage」が目的の言葉を含んでいる
  「damage dealt to enemy: %d」という文字列を、この関数が実際に参照している
```

そのまま「なぜこの候補なのか」まで開けます。点数はすべて内訳つきで、
どれが**事実**でどれが**推測**かの札が付きます。

```
この点数の内訳                                        合計 63 点
  関数の名前が目的の言葉を含んでいる              〔事実〕 +25
  「damage dealt to enemy: %d」を実際に参照している 〔事実〕 +20
  計算した値をメモリへ書き込んでいる（5 か所）      〔事実〕  +8
  値を比べている（1 か所）— しきい値の判定がありそう 〔事実〕  +6
  中で数値の計算をしている（1 回の掛け算）          〔事実〕  +4
```

**名前が一致しただけでは上位に来ません。** 文字列の一致は、
その文字列を実際に参照している命令が見つかって初めて点になります。

## 初心者のための仕掛け

### 1. すべての行に、日本語の意味が付く

ツールバーの **解説** を押すと、命令 1 行ごとに日本語の説明が下に足されます（既定でオン）。
表示は「日本語の文」「式（`x0 = x1 + 8`）」「両方」から選べます。

約 200 種類の ARM64 命令に、専用の説明文を用意しています。
16 進の値には必ず 10 進を添え、レジスタには役割（引数・戻り値・戻り先アドレス…）を添えます。

### 2. 1 行タップで、部品ごとに全部説明

命令をタップすると、その 1 行について次のすべてが出ます。

* ひとことで言うと何をする命令か
* 式で書くとどうなるか
* なぜそうなるのか（背景の説明）
* オペランドの部品ごとの意味（レジスタの役割、即値の 10 進・2 進・文字としての値）
* 飛び先・指し先のアドレス（名前が分かれば名前で）
* **その先に文字列があれば、その中身**
* 実際の 4 バイトと、リトルエンディアンで逆順に見えている理由
* 32 ビットを 2 進数に開いたもの
* 出てきた用語へのリンク

### 3. 2 行組をまとめて解釈する

ARM64 で最初につまずくのが `adrp` + `add` の 2 行組です。
このツールは 2 行を組にして最終的なアドレスを計算し、そこにある文字列まで読んで表示します。

### 4. 学習コース（10 章）と用語集

`？` ボタンから、ゼロから読めるようになるための 10 章が読めます。

1. コンピュータは、実は単純なことしかしていない
2. 0 と 1、バイト、そして 16 進数
3. メモリとアドレス — データはどこに置かれているのか
4. レジスタ — CPU の手元にある 31 個の入れ物
5. 命令を読む（1）代入と計算
6. 命令を読む（2）メモリの読み書き
7. 命令を読む（3）if と for の正体
8. 関数とスタック — 呼んで、帰ってくる仕組み
9. 実行ファイル（Mach-O）の中身
10. 実際に読んでみる — 手順とコツ

用語集には約 60 語が入っていて、解説や学習コースの中からその場で引けます。

### 5. サンプルバイナリを内蔵

手元にファイルがなくても始められるように、練習用の ARM64 Mach-O を
**その場で組み立てて開く** ようにしてあります（`js/sample.js`）。本物と同じ形式で、
関数 6 つ、ループ、文字列参照、外部関数の呼び出し（`__stubs` → `__got`）、
シンボル、`LC_FUNCTION_STARTS` が入っています。

そのうちの `_apply_damage` は、ゲームでいちばんよくある形をそのまま入れたものです。

```
ldr  w8, [x0, #0x20]    ; 今の HP を読む
ldr  w9, [x0, #0x24]    ; 攻撃倍率を読む
mul  w9, w1, w9         ; ダメージ = 攻撃力 × 倍率
sub  w8, w8, w9         ; HP を減らす
str  w8, [x0, #0x20]    ; 同じ場所へ書き戻す
```

さらに、本物と同じ形の **Objective-C のクラス表**も入れてあります。

```
BattleManager
  値:      _hp     (4 バイトの整数, +0x20)
           _attack (4 バイトの整数, +0x24)
  メソッド: -[BattleManager applyDamage:]        ← 上の _apply_damage
           -[BattleManager criticalMultiplier]
```

`_apply_damage` が触っている `[x0, #0x20]` は、この表のおかげで
**「BattleManager の hp」**として表示されます。**自動解析**を開くと
「値を書き換えている場所」の先頭に `BattleManager の hp を計算した値だけ減らす` が出ます。
`地図 → ⚔️ バトル → BattleManager → hp` と降りると、それを書き換えている場所も探せます。

## 「検索」ではなく「参照関係」で絞る

文字列検索だけに頼ると、`damage` を含む文字列が 300 本出てきて終わりです。
このツールは、ファイルを開いたときに **セクションを 1 回だけ舐めて**
プログラム全体の索引を作ります（`js/words.js` + worker の `scanProgram`）。

```
bl の飛び先          → 呼び出しグラフ（誰が誰を呼んでいるか）
adrp + add / ldr     → データ参照（誰がどの文字列・データを見ているか）
語ごとの命令の分類    → 関数ごとの統計（掛け算が何回、store が何か所…）
```

逆アセンブルは通しません。4 バイトの語のビットを直接読むので、
数十 MB の `__text` でも一気に走ります。この索引があるおかげで、

> ×「damage という文字列の近くだから、この関数はダメージ計算っぽい」
>
> ○「この関数は 0x1004A2B0 の文字列を参照していて、BattleManager から呼ばれていて、
>    中で 3 回の掛け算をして、読み込んだ値を同じ場所へ書き戻している」

と言えるようになります。前者は推測、後者は事実です。**この差がこのツールの中心です。**

候補の点数は、独立した証拠の足し合わせで決まります（`js/rank.js`）。

| 証拠 | 点 | 種別 |
| --- | --- | --- |
| 目的の文字列を、この関数が実際に参照している | +20 | 事実 |
| 関数自身の名前が目的の言葉を含む | +25 | 事実 |
| 目的の言葉を含む処理を呼んでいる / から呼ばれている | +12 / +10 | 事実 |
| 数値の計算をしている（掛け算・割り算・小数） | 最大 +12 | 事実 |
| 計算した値をメモリへ書き戻している | +8 | 事実 |
| 値を比べている（しきい値の判定） | +6 | 事実 |
| あちこちから呼ばれている（3 か所以上） | +5 | 事実 |
| 有力候補を呼んでいる / から呼ばれている | +8 | 推測 |
| 命令が 1500 個を超える（目的の計算そのものとは考えにくい） | −6 | 推測 |

点数は「関連度」であって、正解であることの証明ではありません。
確度は `1 − exp(−点数 / 45)` で、**どれだけ証拠がそろっても 100% にはなりません。**

## 機能から関数を探す

関数が 1 万個あるファイルで「この関数はデータをコピーしています」と言われても、
それが**ゲームのどこの処理なのか**は分かりません。そこで、逆から辿ります。

```
アプリの機能（ログイン・課金・ガチャ・バトル…）
  → その機能でしか出てこない言葉（文字列）
    → その言葉を使っている場所
      → その場所を含む関数
        → その関数が何をしているか（Semantic Model）
```

ツールバーの **機能** を押すと、アプリの中の言葉を集めて機能ごとに束ねます。

| 機能 | 例 |
| --- | --- |
| ログイン・アカウント / 課金・購入 / ガチャ・報酬 | 「ログインに失敗しました」「購入を復元しています」 |
| バトル / キャラ育成 / アイテム / クエスト | 「ダメージ %d」「レベルアップ」 |
| セーブ / サーバー通信 / ランキング / フレンド | 「https://api.…/v1/…」 |
| チート対策 / 広告 / 音 / チュートリアル / 設定 | 「jailbreak detected」 |

機能 → 言葉 → 使っている場所、と 3 回タップすれば担当の関数に着き、
着いた先では処理の区切りと日本語の要約がそのまま出ます。

言葉の「濃さ」（●◐○）は、人が読む文言ほど当たりやすいという順です。
**近くに言葉があるだけでは、その関数がその機能そのものだとは限りません。**
あくまで「探し始める場所」として出しています。

また、`libil2cpp` / UnrealEngine / Flutter / React Native の痕跡があれば先に知らせます。
Unity 製ゲームだと、ロジックの大半はこの実行ファイルではなく別のファイルにあるためです。

## 「命令」ではなく「処理」で読む

このツールの中心は、命令の逐語訳ではなく **意味の層 (Semantic IR)** です。

```
ARM64 命令 → 命令の事実 → データフロー → Basic Block
          → Semantic Block → 関数の意味 → アプリの機能 → 日本語
```

画面もこの階層に合わせてあり、上からも下からも辿れます。

```
アプリの機能 → 関数 → 処理 → ARM64        （関数の要約から降りる）
ARM64 → 処理 → 関数 → 呼び出し元 → 機能    （行をタップして遡る）
```

### 例: この 5 行が 1 つの「処理」になる

```
adrp x0, ...
add  x0, x0, ...
mov  x1, x19
mov  x2, #0x10
bl   _memcpy
```

> **▼ データをコピー**
>
> データを別の場所へコピーする処理です。
> ここでは、その処理に渡すデータを用意してから実行しています。
> バイト数は 16 バイトです。
> コピー元が何なのかは、今の解析情報だけでは特定できません。

「x0 がどうこう」「memcpy とは C の関数で…」は 1 行も出てきません。
そして **分からないものは「分かりません」と書きます**。

### 関数の本当の名前を取り戻す

配布用のアプリは自作の関数名を削ってあるので、関数一覧は `sub_100123456` だらけになります。
ところが **Objective-C のメソッドだけは、名前と実装アドレスの対応表がバイナリに必ず残っています**
（実行時にクラス名とメソッド名で探せる必要があるため）。`__objc_classlist` をたどってこれを読みます。

```
sub_100123456  →  -[LoginViewController loginButtonTapped:]
```

名前が戻ると、関数一覧・参照元（XREF）・ビューアの見出し・関数の要約が
**すべて**その名前で表示されます。「ログインボタンの処理はどれ？」に、名前だけで答えが出ます。
関数の切れ目の情報がないファイルでも、メソッドの実装アドレスはそれ自体が確実な関数の先頭なので、
関数一覧の精度も上がります。

対応しているのは従来形式（1 件 24 バイト）と相対形式（1 件 12 バイト、iOS 14 以降）の両方で、
chained fixups で上位ビットに印が入ったポインタもほどきます。
**表の形が想定と違うときは、名前を付けずに黙って飛ばします** — でたらめな名前を付けるのが一番困るので。

### メソッドの名前まで復元する

iOS アプリの動作はほとんどが `objc_msgSend` — 「ある“もの”に、名前を指定して仕事を頼む」形で
書かれています。そこで、呼び出しに渡される名前をポインタ 1 段ごしに読み出します
（`__objc_selrefs` → `__objc_methname`）。

> **▼ 「loginWithPassword:」を呼ぶ**
> ある「もの」に対して「loginWithPassword:」という仕事を頼んでいます。

メソッドの名前は人が付けたものなので、**その関数が何の担当かを知る一番強い手がかり**です。
関数の要約にも呼んでいるメソッド名が並ぶので、名前が削られたアプリでも
「この関数はログイン担当らしい」というところまで辿り着けます。

### 関数レポート — 事実 / 推測 / 分からないこと

関数を開くと、3 つを **別々の欄に、別々の見た目で** 出します。混ぜません。

```
確かなこと（バイナリから直接読めたこと）           〔事実〕
  命令が 20 個ある
  x0 + 0x20 の値を読み、「引き算をする」という計算をして、同じ場所へ書き戻している
  文字列「damage dealt to enemy: %d」（0x100000514）を参照している
  x8 を 0 と比べている
  この関数を呼んでいる場所が 1 か所ある

ここから推測できること                            〔推測〕
  x0 + 0x20 に置かれている値が、この関数が扱っている値そのものである可能性が高い   90%
  探している「ダメージ計算」に関係している可能性がある                          71%

このツールでは分からないこと                      〔不明〕
  この値が実行時に何を意味するかは、静的な解析だけでは確定できません。
```

「不明」の欄は必ず出ます。**限界を言わない解析ツールは信用できない**からです。

### 値を書き換えている場所（変更候補）

「この数値を増やしたい」に対する、このツールの答え方です。

```
0x10000040C
  変更対象: x0 + 0x20
  変更前:   x0 + 0x20 に入っている値
  演算:     引き算をする
  変更後:   その結果を、同じ x0 + 0x20 へ書き戻す
```

`load → 演算 → 同じ場所へ store` の往復が閉じていることは事実として示しますが、
**「ここを変えれば狙った値が変わる」とは言いません。**
その場所が実行時に何を表しているかは、動かして確かめるしかないからです。
画面にもそう書いてあります。

### 処理の流れと、呼び出しの流れ

```
処理の流れ（制御フロー）                呼び出しの流れ
  0x1000003F0  関数の開始                _main
  0x100000410  条件を確認  ◆ 条件で分かれる   ↓
    0x100000418  値を用意する            _apply_damage
  0x100000424  値を書き込む  ▼ 合流         ↓
  0x100000438  関数の終了  ■ 終わり        _puts
```

if / else / ループ / 途中で帰る（early return）/ 異常時の道 を見分けます。
`br xN` のように行き先がレジスタで決まる分岐は、**「分からない」のまま残します。**

### 事実と推測を混ぜない

解析結果には必ず **確からしさ** と **根拠** が付きます。

| 段階 | 意味 | 例 |
| --- | --- | --- |
| 確実 (confirmed) | バイナリから直接読める | この 2 行はアドレス `0x1000043C` を作っている |
| ほぼ確実 (high) | 呼び先の名前から分かる | データをコピーしている |
| 推測 (inferred) | 状況からの推測 | 通信に渡すデータを作っていそう |
| 情報不足 (unknown) | 手がかりがない | このデータが何かは特定できません |

「データをコピーしている」は根拠つきで言いますが、
**「ユーザー名をコピーしている」は別の証拠がない限り言いません。**
画面左の帯も、確からしさが低いまとまりでは薄く表示されます。

### 追いかけているもの

* レジスタ→レジスタ、定数→レジスタ、メモリ→レジスタ、レジスタ→メモリ
* 呼び出しの戻り値→レジスタ、レジスタ→呼び出しの引数
* `adrp` + `add` のアドレス組み立て、スタックに置いた値の読み直し
* 「今このレジスタが何を持っていそうか」（確保されたメモリ／第 1 引数／文字列「Hello」の場所／**不明な値**）
* `load → 演算 → store` の往復（＝値の増減が起きている場所）
* ある行が作った値の **行き先**（次にどこで読まれ、何に渡され、いつ上書きされるか）
* 定数との比較（しきい値の判定）と、何度も読み書きされている場所

分岐で飛び込まれる場所では、追跡していた前提をいったん **捨てます**。
そこで欲張ると根拠のない断定が生まれるためです。
値の追跡も、上書きされた行か合流点で打ち切り、その理由を画面に書きます。

## 使い方

1. ページを開いて **サンプルで練習する**、または **ファイルを開く** からバイナリを選びます。
2. Mach-O は自動で認識され、`__TEXT,__text` が選ばれて逆アセンブルされます。
3. **アセンブリ / 16進** で表示を切り替え。**解説** で日本語の注釈を出し入れします。
4. 行をタップすると詳細、長押しでメニュー。
5. **選択** で範囲コピー。開始行をタップしたあと、もう 1 行タップすると範囲が決まります。

ハードウェアキーボード: `⌘F` 検索、`⌘G` または `G` ジャンプ、`E` 解説の切り替え、
`?` ヘルプ、矢印 / PageUp / PageDown / Home / End で移動、`Esc` で閉じる。
`⇧` を押しながら移動キーで範囲を伸ばし、`⌘A` で全選択、`⌘C` でコピー。

**設定**（`⋯`）から、テーマ・文字の大きさ（4 段階）・解説の書き方・表示言語（日本語 / English）を変えられます。

## 大きなファイルでも軽い理由

* **最初にまとめて逆アセンブルしない。** 4 KiB ごとのチャンクを、必要になったときだけ
  worker で逆アセンブルし、64 個ぶんを LRU キャッシュに置きます。
* **画面に出ている行だけが DOM にある**（40〜50 要素）。スクロール中に要素の生成も破棄も起きません。
* **スクロール領域は 6,000,000 px で頭打ち。** 端に近づいてスクロールが止まったところで
  窓を張り直し、同じ量だけ `scrollTop` をずらすので、画面は動かず慣性スクロールも途切れません。
  32 MB の `__text`（840 万命令）でも端から端まで 60 fps で流れます。
* **アドレスは全部 BigInt。** ARM64 は命令長が固定なので `アドレス = 区画の先頭 + 行 × 4` が厳密に成り立ちます。
* **解説文はキャッシュ**（ニーモニック＋オペランドをキーに 4000 件）。同じ命令の繰り返しは 1 回しか組み立てません。
* **走査系（文字列抽出・相互参照・関数の推測・プログラム索引）は Capstone を通さず、
  4 バイトの語を直接デコード**します（`js/words.js`）。逆アセンブルより桁違いに速いので、
  数十 MB のセクションでも一気に走ります。
* **プログラム全体の索引は 1 ファイルにつき 1 パスだけ。** 呼び出しの辺・データ参照・
  語ごとの命令分類を同時に集め、転送可能な型付き配列で返します（コピーは起きません）。
  索引の中身は 4〜8 バイト／件で、呼び出し元の検索も参照元の検索も二分探索です。
  コードが 24 MB を超えるファイルでは、概要画面での自動走査をやめて、
  利用者が「詳しく調べる」を押したときだけ走らせます。
* **意味解析はスクロールでは絶対に走りません。** 走るのは「利用者が関数を開いたとき」だけで、
  結果は関数単位でキャッシュされます。向きは常に

  ```
  解析 → Semantic Model → キャッシュ → Viewer
  ```

  で、Viewer から解析を呼ぶことはありません。ビューアが持つのは
  「行 → 見出し」の表だけで、描画中に計算は起きません。
* **モデルは言語に依存しません。** 日本語 / English を切り替えても再解析はせず、
  見出しの文字列を作り直すだけです。

## できないこと・気をつけること

* **逆アセンブルは ARM64 (AArch64) だけ**です。他の CPU の Mach-O も、ヘッダ・セクション・
  バイト列は読めますが「アセンブリ」タブは使えません。
* **App Store 版のアプリ（`cryptid = 1`）は読めません。** `__TEXT` が暗号化されたままなので、
  意味のある命令にはなりません。開くと警告が出ます。実機から復号済みの状態で取り出したものが必要です。
* **名前が削られたファイルでの関数の切れ目は「推測」です。** `bl` の飛び先と、
  `ret` の直後にあるプロローグらしい命令を手がかりにしています。
  取りこぼしはありますが（呼ばれない小さな関数など）、誤検出は出にくいようにしてあります。
  画面にも推測である旨を表示します。
* **関数の要約も推測です。** 命令の並びから読み取れることだけを書いています。断定ではありません。
  そのぶん、どの説明にも確からしさと根拠を添えています。
* **データフローは簡易版です。** 完全な SSA ではなく、ARM64 の定型（`adrp`+`add`、
  呼び出し規約、スタックへの退避）に強い線形の追跡です。合流点では前提を捨てるので、
  取りこぼしはありますが、誤った断定は出にくくしてあります。
* **意味づけできる外部 API は、表に載っているものだけです。** 知らない名前は
  「この名前が何をするものかは、このツールにはまだ情報がありません」と表示します。
* **候補の★や％は「関連度」で、正解の証明ではありません。** 独立した証拠を足した結果で、
  どれだけそろっても 100% にはなりません。必ず内訳を開いて、事実の部分を自分で確かめてください。
* **「ここを変えれば値が変わる」とは言いません。** 読み書きの往復が閉じていることは示しますが、
  その場所が実行時に何を表すかは静的解析では決められません。最後は動かして確かめる必要があります。
* **自動解析が見るのは、あくまで一部です。** 深掘り（実際に命令を読む）のは上位の十数個だけで、
  その数は画面に書いてあります。「全部調べた」とは言いません。
* **行き先が実行時に決まる呼び出し（`objc_msgSend`・関数ポインタ・`br xN`）は追えません。**
  呼び出しグラフにも出てきません。iOS アプリの動作の大半がこの形なので、ここは大きな穴です。
* **フィールド名が読めるのは Objective-C のクラスだけです。** Swift の struct、C++ のクラス、
  Unity(il2cpp) のフィールドには、この表がありません。その場合 `x0 + 0x20` は
  `x0 + 0x20` のまま表示します（分からないものに名前を付けないため）。
* **同じ位置を触っているだけの命令は、別のクラスのものかもしれません。**
  値の検索結果には「このクラス／別のクラス／クラス不明」の札を必ず付けています。
* **部品分け（地図）は推測です。** 材料（クラス名・参照文字列・呼んでいる API）は
  すべて実在しますが、そこから担当を決めているのはこのツールです。
* C++ の名前復元、Swift のメタデータ、デコンパイル（C 言語への復元）は入っていません。
* 学習コースと用語集は日本語のみです。UI と命令の解説は英語にも切り替えられます。

## 開発時の確認方法

### 解析のテスト

```sh
node tests/run.js      # または npm test
```

ブラウザも Capstone も要りません。逆アセンブル済みの文字列（Capstone が実際に吐く形）を
`js/blocks.js` に直接食わせて、モデルの中身を確かめます。見ているのは

* 命令の語 — 実物のエンコード（`llvm-mc` が吐いたバイト列）で分類・飛び先・
  メモリのずらし幅が合っているか。SIMD の 128 ビット転送のような、
  **間違えると別のアドレスを指してしまう**ところを重点的に。
* 索引 — 呼び出し元 / 呼び出し先 / 文字列の参照元 / 関数ごとの命令統計
* ランキング — **名前だけの一致が、参照と命令の裏づけのある関数より上に来ないこと**、
  点数の内訳の合計が表示と一致すること、手がかりがなければ候補を作らないこと
* データフロー — read→演算→write の連鎖、値の行き先、しきい値、reg→reg / imm→reg /
  mem→reg / reg→mem / call→reg / reg→呼び出し引数
* 制御フロー — if / else / 合流 / ループ / 途中で帰る / 行き先不明
* レポート — 事実・推測・不明が混ざらないこと、推測に必ず確度と根拠が付くこと、
  変更候補に必ず但し書きが付くこと
* 自動解析 — 指示なしで目的別の候補まで出ること、中断できること、
  手がかりがゼロでも「見つからなかった」と言えること
* 証拠の合成 — 候補が多いほど同じ証拠でも確からしさが下がること、
  **同じ系統の証拠をいくら並べても確定にならないこと**、打ち消す証拠が効くこと、
  内訳の掛け算が表示している確率と一致すること
* 検証 — getter / setter を逆アセンブルして位置の一致を確かめられること、
  **位置が食い違うときに一致したことにしないこと**、長すぎる関数をアクセサと呼ばないこと、
  self を持ち回っているレジスタだけを self として数えること
* 特定 — 目的を選ぶだけで値が 1 個に決まること、上限（`_maxHp`）を今の値より上に出さないこと、
  型が合わない値を候補から外すこと、**命令を 1 つも読まずに確定と言わないこと**、
  逆アセンブルの回数が予算で頭打ちになること、クラス表がなくても形から場所を出せること、
  そして名前が読めない相手を確定と呼ばないこと
* クラスとフィールド — 実際に組み立てたサンプル Mach-O のクラス表から、
  メソッドと ivar（名前・型・位置）が取れること、`[x0,#0x20]` が `self.hp` に解決されること、
  **self でないレジスタ経由を self と言い切らないこと**
* 地図 — クラス名から担当を見分けられること、部品に束ねられること、
  クラス表がないときは粗い地図だと分かること
* ひとこと — 値の変更が 1 行で言えること、変更がないときも別の言い方に落ちること
* 異常系 — 不完全な命令列、不明な命令、分岐先不明、シンボルなし、API 名なし、追跡不能

異常系ではクラッシュしないことに加えて
**「解析できませんでした」「情報不足」と言えているか** まで確認します。

### 精度の測定 — 本物のアプリで、機能ごとに割合を出す

`node tests/run.js` は「作った命令列で、思ったとおりに動くか」を見るテストです。
**本当に当たっているか**は、それだけでは分かりません。実際、synthetic なテストが
157 本すべて緑のまま、本物のアプリでは

* Objective-C のメソッド呼び出しの行き先が **16414 か所すべて不明**
* 呼び出し関係の **28% が上限で黙って捨てられていた**
* 文字列の **32% が上限で消えていた**
* アクセサの役割が **1 件も言えていなかった**

という状態でした。これを見つけるには、実物のバイナリで測るしかありません。

```sh
pip install lief capstone
python3 tests/oracle.py tests/battlecats tests/oracle.battlecats.json.gz   # 正解表（1 回だけ）
node --max-old-space-size=8000 tests/accuracy.mjs
```

`tests/oracle.py` は **このツールとは別実装**（python + lief + capstone）で同じバイナリを読み、
「本当はこうなっている」を書き出します。材料はバイナリ自身が持っているものだけ
（`LC_FUNCTION_STARTS` / `LC_SYMTAB` / chained fixups / `__objc_*` / capstone）。
`tests/accuracy.mjs` は **画面と同じコード**（`js/worker.js` をそのまま Node で起こす）を
走らせて、機能ごとに突き合わせます。


問いはすべて **答えが 1 つに決まるもの**だけにしてあります。たとえば
「うろ覚えの名前から場所を決める」では、打ち込む語がバイナリ全体で 1 つの変数名にしか
入っていない場合だけを出題します。どちらを答えても正解になる問いで測っても、

```sh
node tests/accuracy.mjs --only=objc,calls        # 機能を絞る
node tests/accuracy.mjs --save=before.json       # あとで比べるために残す
node tests/accuracy.mjs --base=before.json       # 前回との差だけ出す
```

**採点の対象になっていない変更は、精度を上げた変更ではありません。**
スコアリングや解析に手を入れたら、必ず `--base` で前後を比べてください。

### サンプルバイナリ

`js/sample.js` が組み立てるバイナリは、実物の Mach-O として検証できます。

```sh
# サンプルを書き出して、Mach-O として正しいか確かめる
node -e "import('./js/sample.js').then(m=>require('fs').writeFileSync('/tmp/s.bin',m.buildSampleBinary()))"
llvm-objdump --macho --private-headers /tmp/s.bin
llvm-objdump --macho -d --syms --indirect-symbols /tmp/s.bin
```

命令の解説を新しく足したときは、`llvm-mc` で命令列を組み立て、Capstone で
オペランドの書式を確かめてから `js/arm64.js` のハンドラを書くのが確実です。
